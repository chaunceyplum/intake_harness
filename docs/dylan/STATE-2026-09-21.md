## Activation — wired, and not yet possible

Building the audience was only half the job and the pipeline was reporting
"built" as finished. `src/lib/agents/audience/activation.ts` now closes that,
and it is deliberately off unless the brief names a destination.

It uses `destination_update_dataflow_audiences` — "add or remove activated
audiences on an existing destination dataflow". Worth knowing: an earlier
design in this repo concluded that no such tool existed and worked around it by
creating an *additional* dataflow per segment. The tool does exist, so that
workaround is not used.

The allow-list is the guardrail. `destination_list_dataflows`,
`destination_get_dataflow` and `destination_update_dataflow_audiences` are
permitted for the audience agent. `destination_create_dataflow`,
`_create_base_connection` and `_create_target_connection` are deliberately
**not**, so the agent cannot invent a destination whatever any future code in
it tries to do.

**Why it cannot fire today.** Read live on 21 Sep 2026: the `tapdemo` sandbox,
where the demo's segments live, has 20 dataflows and **not one is a
destination** — they are all `Datalake to UPS/UIS`, per-dataset flows, `UPS
Export`, `File Upload`. The real destination dataflows ("Chaunceys Audience s3
dest", "AdobeCampaignProfilesZP") are in the **prod** sandbox, which is a
different sandbox from the one holding the audience.

So activation returns `declined` with what a human must do, which is the
correct behaviour and not a bug. **To make activation work, somebody has to
create one destination in AEP for sandbox `tapdemo` and connect a dataflow to
it.** After that the agent activates to it with no code change.

A trap worth recording: the destination tools default to `sandbox: "prod"`. A
listing taken without the sandbox shows prod's dataflows, which is how a first
probe concluded the tenant had destinations when the sandbox that matters has
none. The harness has `AEP_SANDBOX=tapdemo` set and passes it explicitly.

## Open, and needing a person

1. **The audience build has still never been proven end to end.** The
   direction fix and the deduplication are deployed and verified as functions.
   The last real run built the inverse of the brief and reported `completed`.
   This is the biggest open risk and it cannot be closed without a real
   Workfront approval and a real segment build.
2. **The live segment still has the duplicate.** "Fall Video Attach-v2"
   (`5571c4f6-84c5-4611-8844-a7027f731ea3`, sandbox `tapdemo`) reads
   `xfinityInternet = true and xfinityTV = false and xfinityInternet = true and
   xfinityTV = false`. It was built before the fix; the fix stops new ones and
   does not reach back. Repairing it is one `adobe_update_segment` call with
   the deduplicated PQL.
3. **No destination in `tapdemo`** — see above.
4. **Stray containers, and the `Exited (137)` they explain.**
   **Corrected 22 Sep 2026** — this entry first said the harness "dies on its
   own" with "memory fine", which was wrong and would send the next reader
   after a memory leak that does not exist.

   Measured after the third occurrence: `OOMKilled=false`, exit code 137,
   2.8 GB available, nothing in the kernel OOM log, and a harness log showing
   a clean startup then silence. That combination is SIGKILL from **outside**
   the container, not the OOM killer — and the only thing here that sends it
   is `docker rm -f harness`, the first line of `up-harness.sh`. Each time,
   a container on the other image tag (`harness:latest`) appeared afterwards
   with no port mapping and no env file, which is the bare-`docker run` trap
   in README section 4 happening in practice.

   So: a deploy that half-succeeds, not a flaky box. Two strays were present
   on 22 Sep — `relaxed_banzai` (running, no ports) and `adoring_moore`
   (exited). Removing them needs a person, and hardening `up-harness.sh` so
   it cannot leave nothing running would remove the cause.
5. **`workfront-inhouse` is a dead MCP registration** — route never deployed,
   404 every time, no agent calls it. It shows as a WARN in the readiness
   check. Remove it in Settings.
6. **`DE:Key Objectives & Success Metrics`** receives the business objective
   and drops the success metrics the marketer wrote. The field name has an "&"
   in it and should carry both.
